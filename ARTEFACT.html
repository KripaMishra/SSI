1. Problem Summary

Build an AI assistant that answers three question types over structured sales data and unstructured text documents:

TypeExampleOutput Contract
WHAT"What were GlucoJoy's monthly primary sales vs target in North region in November 2025?"Factual response with data + citations
WHY"Why did SparkClean 1kg primary sales spike in Mumbai in the week of 16 Sep 2025?"Causal analysis; citations mandatory
WHAT_TO_DO"What should we do about declining sales in Delhi?"Recommendation; status = PENDING_APPROVAL

Key constraints: Stateless agent (no conversation memory), raw data has quality issues (sentinels, negatives, mixed formats, PII), must handle high traffic via async queue, responses must cite sources.

Key Modelling Decisions

  • Star schema — 4 dimensions, 2 facts, 2 supporting tables. All fact tables reference dimensions via FKs.
  • sales_units_flag — Tracks data quality provenance on each row so the agent can adjust confidence. Not a standard data warehouse column, but essential for this use case where 2.4% of rows have unreliable values.
  • base_mrp as VARCHAR — Preserved from CSV dtype to avoid coercion errors. The ORM maps it as String.
  • FK naming inconsistencies — fact_targets.material_no (should be sku_code), fact_targets.area (should be territory), stockouts.item_code, promotions.sku — all documented in the data dictionary.

Limitations & Future Work

  • Current: TTL-based invalidation — naive, no awareness of data updates.
  • Better: Invalidate on data update events (e.g., after new CSV ingestion) + pre-synthesize cache entries for frequently queried topics.
  • Better: Use Redis vector search (RediSearch) instead of scanning all keys and computing cosine similarity in Python — O(n) scan vs O(log n) HNSW index.

8. Risk Awareness & Trade-off Reasoning

8.1 Risks

Risk: Incorrect query generation — The LLM may generate wrong SQL-equivalent filters (e.g., joining on wrong columns, applying incorrect date ranges).
Mitigation: describe_database() provides schema context on every invocation. The query_database tool is an ORM wrapper with typed parameters, not raw SQL — this limits the blast radius. The agent iterates via tool loop: if a query returns unexpected results, it can self-correct in the next cycle (timeout-permitting).
Risk: Hallucinated responses — The LLM may invent numbers or cite non-existent sources, especially for WHY questions that require causal reasoning.
Mitigation: WHY intent enforces citations.length > 0 at the validation layer. Citations come from tool outputs (ChromaDB doc IDs, relational DB query params), not from the LLM's internal knowledge. The finalize node uses structured output (with_structured_output + json_mode), reducing free-form hallucination surface.
Risk: Data misinterpretation — The LLM may treat nulled sentinel values as meaningful, or confuse fact_targets.area with fact_primary_sales.territory.
Mitigation: sales_units_flag column with explicit semantics in the system prompt instructs the agent to treat non-ok rows as unreliable. The system prompt documents the FK naming inconsistencies (material_no = sku_code, area = territory) so the agent maps correctly.

8.2 Trade-offs

Single agent vs. multi-agent system. The PRD requested a multi-agent system. A single agent with a tool loop was chosen because: (1) the scope is narrow (3 question types, 3 tools) — multi-agent supervision would add latency, token waste, and state management complexity without proportional benefit; (2) the agent is stateless per request — no conversation memory to distribute across agents; (3) the tool loop already provides the core multi-agent benefit (decomposition + delegation) within a single LLM context window.
ORM wrapper vs. raw SQL. The query_database tool wraps SQLAlchemy ORM instead of running raw SQL. This limits query complexity (no subqueries, CTEs, window functions) but prevents SQL injection and keeps the agent from generating malformed queries. A read replica with raw SQL execution would be more powerful but requires stricter access control and query validation.
deepseek-v4-flash vs. lighter model. The chosen model is overkill for this task and slower than alternatives. Used due to resource constraints on gemini-flash-lite. A production deployment should use a faster, cheaper model like gpt-4o-mini or gemini-2.0-flash-lite.

9. Agentic Construct

StepNameInputOutputHandoffFailure Path
1Classify Intent User question Intent (WHAT/WHY/WHAT_TO_DO/OUT_OF_DOMAIN) → Step 2 (if in-domain) OUT_OF_DOMAIN → ABSTAINED → respond
2Gather Schema Intent Database schema description → Step 3 Tool error → ERROR → respond
3Query & Retrieve Schema + question Query results + doc results → Loop to Step 3 (if more queries needed) or → Step 4 Tool error → ERROR → respond
4Synthesize & Validate All tool results AgentResponse with citations → Respond Validation failure → ResponseValidationError → 500

The agent iterates between Steps 2 and 3 (the tool loop) until the LLM decides it has enough data. The loop is bounded by a 180-second timeout.

11. AI Tool Usage Reflection

  • Primary tool: OpenCode (Cadra) — used as the sole coding agent throughout development.
  • Effective: Long-running multi-step tasks with explicit step-by-step breakdowns. Documentation lookup when source is explicitly named.
  • Ineffective: Doesn't auto-detect ctxMode (had to prompt explicitly). Misses LSP warnings unless flagged. Used deprecated LangGraph APIs (manual JSON parsing instead of with_structured_output). Returned HTTP 200 on agent timeouts — a basic error.
  • Friction: Forgot to load env vars during setup config. Had to rework from python-rq to QStash mid-development, burning AI credits that could have been used for review loops.
  • Prompt history: All working prompts archived in working_prompts/.

12. Future Improvements

  1. Evals suite: Systematic benchmarking of agent responses against ground-truth queries. No evaluation framework exists today.
  2. Cache invalidation: Replace TTL with data-update-triggered invalidation. Pre-synthesize cache for high-frequency topics.
  3. Faster model: Replace deepseek-v4-flash with a lighter model (e.g., gpt-4o-mini, gemini-2.0-flash-lite) for lower latency.
  4. Raw SQL access: Read replica with parameterized raw SQL would allow complex queries in a single call vs. multiple ORM calls.
  5. Redis vector search: Replace O(n) Python cosine similarity scan with RediSearch HNSW index.
  6. Multi-agent (if justified): Add a supervisor agent only if the tool set grows beyond 5-6 tools or the agent needs long-term memory.
  7. Fix Langfuse tracing: Debug Vercel deployment integration.
